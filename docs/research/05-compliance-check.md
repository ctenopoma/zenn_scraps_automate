# 05. Zenn のルールとの照合（場つなぎ方式: 専用プロファイルの Playwright + ページ内 fetch）

調査日: 2026-10-01。対象は、04 で場つなぎとして選んだ方式。

- 人がメール（確認コード）で一度ログインした、Zenn 専用のブラウザプロファイルを Playwright で開く。
- zenn.dev のページの中から、フロントエンドと同じ内部 API（02 の追記）を fetch で呼び、自分のスクラップを作ってコメントを投稿する。

## 結論

**明示的に違反する条項は見つからなかった。** 自動化ツール、非公式 API、ブラウザ自動化を名指しで禁止する条文はない。

ただし、次の2点は「書き方しだいで違反になりうる」ので、条件を守る前提で進める（下の「守る条件」）。

1. 第4条11号のスパム（「機械により自動生成された文章の投稿」）と、AI 方針の「ボットを用いてアカウントを自動運用する」への懸念
2. 第4条16号の包括条項（「運営者が不適切と判断する行為」）。基準は開示されていない

## 【推測】として残る点

- #569 と #209 の回答は、どちらも**読み取り**（記事一覧の取得など）についての質問への回答。自分のセッションで**書き込む**ことについて、運営の発言は見つからなかった。ただし、書き込みもフロントエンドと同じリクエストを本人のブラウザから送るだけで、画面から投稿するのと区別できない。
- 公式の Public API（01）は、API 経由の投稿を `posting_route: "api"` として区別して記録する。内部 API での投稿は `"web"` と記録される。区別を避ける目的ではないが、運営から見ると人の操作と見分けがつかない。Public API が開放されたら、すぐに切り替える。
- 包括条項（第4条16号）の基準は非公開なので、「違反しない」と断定はできない。

## 守る条件（ツールの仕様に組み込む）

1. **人がレビューしてから送る。** 既定は dry-run にする。送る本文の一覧と sha256 を表示し、`--execute` を付けたときだけ送信する。
2. **人が実行を指示する。** 定期実行（cron、タスクスケジューラ）や CI での無人実行はしない。README にも書く。
3. **少量にする。** 1日の件数に自前の上限を設ける（既定 20 コメント）。1件ずつ順に送り、間を数秒あける。
4. **止まる条件を広めにとる。** 429 / 422 / 403、ログイン切れ、想定外の応答では、その場で止める。POST は再試行しない。
5. **同じ本文を二度送らない。** 投稿済みの本文は `meta.yml` の sha256 で判定する。
6. **CAPTCHA や確認画面を回避しない。** 応答に CAPTCHA の要求などが含まれていたら止める。自分のスクラップへの投稿では CAPTCHA は要求されない（02 の追記）。
7. **上限を探らない。** 上限の基準は「外部からの検証やそれに基づいた回避行為を防ぐため」非公開とされている。上限に当てて応答を観測する目的の投稿はしない。04 と HANDOFF にあった「日次上限に当たったときのレスポンスを観測する」作業はやめる。自然に当たったときだけ記録する。
8. **秘密を書かない。** 送信前に、API キーや Cookie のような文字列がないか簡易な secret scan をかける。Zenn 本体の検出機能はメールで通知するだけで、公開は止めない（01 の追記2）。
9. **スクラップだけに使う。** 記事・本の投稿には使わない（GitHub 連携と zenn-cli を使う）。
10. **Public API が開放されたら切り替える。** 送信部分（transport）を差し替える作りにしておく。
