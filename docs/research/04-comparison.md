# 04. 方式比較と暫定方針

調査日: 2026-10-01。評価は 00〜03 の事実をもとにした判断（推測を含む）。

## 比較表

| 方式 | 正当性 | 実行時トークン | 本文の忠実性 | 速度 | 壊れやすさ | 認証情報リスク | 無人/CI | 初期実装 |

| **01 公式 Public API（zenn-cli）** | ◎ 公式（`posting_route: api`） | ほぼ0 | 高 | 数秒 | 中（実験的機能） | 低（スコープ・期限付きキー） | ○ | **低** |

## 暫定方針

1. **投稿経路は 01 の公式 Public API を第一候補にする。**
   - まずは zenn-cli（`zenn scrap`）をそのまま使い、足りない部分だけ薄いラッパーを書く。
   - Cookie もブラウザも使わない。
2. **LLM の役割は「Markdown を書く」ことまで。** 投稿は決定的に動く CLI に任せ、実行時のトークン消費をほぼ0にする。
3. **リポジトリが真実の源（source of truth）。**
   - `scraps/<topic>/` に、`meta.yml` と `NNN.md`（1ファイル = 1コメント）を置く。
   - 投稿結果（slug、comment slug、本文の hash）は state ファイルに書き戻す。
4. **安全装置**
   - dry-run を用意する。
   - 自前のレート制限（1日N件）を設ける。
   - 429 / 422 が返ったら即停止する。
   - POST は再試行しない（zenn-cli と同じ方針）。
   - 最初は `unlisted: true` でテストする。
5. **検証は GET で行う。** 投稿後に `GET /scraps/{slug}` で取得し、コメント数と本文をローカルと照合する。
6. **Public API が使えなかった場合のフォールバック**
   - 02（Cookie を手動で渡す）か 03-D（拡張機能）を使う。
   - 03-C（LLM ブラウザ操作）は、調査・診断用に限る。
