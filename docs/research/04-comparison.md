## 暫定方針（2026-10-01 改訂）

当初は 01 の公式 Public API を第一候補にしていた。しかし、ログインした状態でも APIキーの発行画面（`/settings/api-keys`）が 404 だった。そのため **当面は使えない** と判断した（01 の追記を参照）。

1. **投稿経路を差し替えられる作りにする。** リポジトリの形式、状態ファイル、レート制限、検証は共通にし、送信部分（transport）だけを切り替える。
   - `public-api`: Bearer キーで送る。公開されたら本命にする。
   - `internal-api`: Cookie で送る（02）。
   - `browser`: 拡張機能やユーザースクリプトから、同一オリジンで fetch する（03-D）。
2. **当面の送信経路は、次の3つから選ぶ。**

   | 案 | 内容 | 長所 | 短所 |
   |---|---|---|---|
   | A | 内部API + 手動で取得した Cookie（ローカル実行のみ） | 実装が最小で、すぐ動く | Cookie はアカウント全権を持つ。非公式なので変更されうる。セッションが切れたら手で更新が必要 |
   | B | ユーザースクリプト / 拡張機能から同一オリジンで fetch | Cookie を外に出さない。本物のブラウザから送るので検知されない | ブラウザが起動している必要がある。エージェントからの呼び出し方を設計する必要がある |
   | C | Public API の公開を待つ。それまでは Markdown を手で貼る | リスクがゼロ | 自動化できない |

3. **LLM の担当は Markdown を書くところまで。** 投稿は決定的に動く CLI に任せ、実行時のトークン消費をほぼ0にする。
4. **リポジトリを正とする。**
   - `scraps/<topic>/` に `meta.yml` と `NNN.md`（1ファイル = 1コメント）を置く。
   - 投稿結果（slug、comment の id / slug、本文の hash）は `meta.yml` に書き戻す。
5. **安全装置**
   - dry-run で事前に確認できるようにする。
   - 自前でレート制限をかける（1日N件まで）。
   - 429 / 422 が返ったら、その場で止める。
   - POST は再試行しない。
   - 最初は `unlisted: true` でテストする。
6. **検証は GET で行う。** 投稿後に取得し、コメント数と本文をローカルと照合する。
   - 本文の照合: 内部APIの `blob.json`（ログインが必要）なら `body_markdown` を比べられる。
   - 認証不要の `GET /api/scraps/{slug}` は `body_html` しか返さないので、件数と slug の照合までになる。
   - Public API の `GET /public-api/v1/scraps/{slug}` も、コメントは `body_html` しか返さない（OpenAPI で確認、01 の追記2）。どの経路を使っても、Markdown で照合できるのは `blob.json` だけ。
7. 03-C（LLM にブラウザを操作させる）は、調査と診断の用途に限る。
