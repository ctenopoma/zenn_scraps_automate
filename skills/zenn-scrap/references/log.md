# 調べたこと・試したことを記録する

目的は、作業の途中で「わかったこと」をまとまりごとにスクラップへ残すこと。
作業の全部を最後に1つの長文で返すと、読む側は追えない。区切りごとに1コメントにし、チャットにはその区切りの要約と結論を返す(5 節)。

## 1. スクラップを決める

- **既存のスクラップに追記する** テーマが同じなら追記する。`<原稿リポジトリ>/scraps/` を見て、近いものがあればユーザーに確かめる
- **新しく始める** `scraps/<topic>/` を作る。`<topic>` は英小文字とハイフン(例: `duckdb-trial`)。`meta.yml` は次の形

```yaml
title: "DuckDB を試す(調査ログ)"   # 100 文字まで。何を調べたかが分かる題
topic_names: [duckdb, python]       # 5 件まで。Zenn のトピック名(英小文字)
unlisted: true                      # 限定公開。作成時にしか選べず、公開はあとから画面で切り替えられる
closed: false
can_others_post: false              # 他人の書き込みは閉じる(LLM が読むときの混入を避ける)
# --- 以下は投稿ツールが管理(手で編集しない) ---
slug: null
comments: []
```

限定公開にするか、最初から公開にするかは、新しく始めるときにユーザーに聞く。迷ったら限定公開にする。

## 2. 区切りの付け方

次のどれかが起きたら、そこまでを1コメントにする。コマンド1つごとには書かない。

- 問いに答えが出た(「〜は〜だった」)
- 仮説が確かめられた、または外れた
- 方針を決めた、または変えた(理由も書く)
- 失敗して、原因が分かった(再現手順と直し方も書く)
- 調べるのをやめた(どこまで分かって、何が残ったか)

1コメントは 300〜1,500 文字を目安にする。上限は 20,000 文字だが、長いものは2つに分けたほうが読みやすい。

## 3. 1コメントの書き方

```markdown
## <わかったことを一言で>

<結論を1〜2文>

- <根拠。出典の URL、または実行したコマンドと結果の要点>
- <推測は文末に「(推測)」>

<次にやること(あれば)>
```

- 見出しは「何をしたか」より「何がわかったか」にする(例: 「インストール」ではなく「pip では入らず uv なら入った」)
- コマンドの出力は要点だけを引用する。長いログは貼らない
- 前のコメントとのつながりが必要なら「(前のコメントの続き)」と1行書く
- 書き方の約束が原稿リポジトリの CLAUDE.md にあれば、それに従う

## 4. ファイルにして、送る

1. 次の番号を決める。`scraps/<topic>/` の `NNN.md` の最大の番号 + 1(投稿済みかどうかに関係なく)
2. `scraps/<topic>/NNN.md` に書く
3. `zs post <topic>` で dry-run する。秘密情報らしき文字列や文字数の超過は、ここで止まる
4. 送ってよいテーマなら、[post.md](post.md) の手順で送る。送ってよいか分からなければ、ユーザーに聞く
5. チャットに、この区切りの要約と結論を返す(次の節)

1日の上限(既定 20 コメント)に近いときは、区切りを大きめにまとめるか、残りを翌日に回す。

## 5. チャットに返すもの

チャットは「いま追う」ため、スクラップは「あとで読み返す」ため、と役割を分ける。
区切りごとに、要約と結論をチャットにも出す。番号と見出しだけにすると、何が分かったかを知るたびにスクラップを開くことになり、会話が途切れる。

```markdown
**[NNN] <見出し>** — 送信済み: <スクラップの URL>
要約: <何をして、何がわかったかを2〜4文>
結論: <1〜2文>
次: <次にやること(あれば)>
```

- コマンドの出力、出典の一覧、長い表はチャットに貼らず、スクラップにだけ書く
- 送っていないときは「送信済み」の代わりに「未送信: 送ってよいですか?」と書く
- セッションの最後は、各区切りの結論を並べるだけにする。同じ説明を繰り返さない

## してはいけないこと

- 投稿済みの `NNN.md` を書き換える(訂正は次の番号で)
- 調べていないことを、調べたように書く。試していない手順は「試していない」と書く
- 会話の中のユーザーの個人情報や、秘密の値を写す
