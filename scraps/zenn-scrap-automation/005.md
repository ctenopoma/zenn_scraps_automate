## 候補2：ブラウザ自動化いろいろ

| 方式 | 一言 |
|---|---|
| Playwright で画面操作 | トークン0で決定的に動く。ただし UI が変わると壊れ、headless は検知されうる |
| ハイブリッド（Playwright はログインだけ、投稿は API） | Cookie コピーは要らなくなるが、非公式APIのリスクは残る |
| LLM にブラウザを操作させる（Playwright MCP / Claude in Chrome / Computer use） | 実装は楽。でも1件あたり**数万〜十数万トークン**かかり、本文が改変されるリスクもある |
| 拡張機能 / ユーザースクリプト | 同一オリジンで fetch するので Cookie を外に出さずに済む。ただしブラウザ常駐が必須 |
| CDP で既存の Chrome に接続 | Chrome 136 以降、既定プロファイルでは使えない。デバッグポートから Cookie が丸見えになる |

共通の壁は **Google ログインの自動化が事実上できない**こと。参考：[Google のヘルプ](https://support.google.com/accounts/answer/7675428)、[Playwright の issue](https://github.com/microsoft/playwright/issues/19420)。
結局「人が一度ログインしたセッションを使い回す」形になる。

LLM にブラウザを操作させる方式は、**調査や壊れたときの診断用**と割り切るのがよさそう。
- Playwright MCP 自身の README にも「エージェントには CLI のほうがトークン効率が良い」と書かれている。
